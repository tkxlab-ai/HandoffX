### 2026-04-21 — 5-Expert Review 的"选择性接受"原则
- **背景**: 5 专家审查返回 53 条 issue（5 P0 + 23 P1 + 25 P2）。全部修 ≈ 数天；但专家视角与项目现实有系统性偏差——Weber 用银行核心系统标准评 markdown 工具、Tanaka 与 Chen 建议互相矛盾（一个嫌多一个嫌少）。
- **选项**:
  - A：按评分 P0→P1→P2 全量修
  - B：按「成本 × 收益 × 不修代价」三维筛出"真 bug + quick win"，其余显式拒绝并记录理由
  - C：完全忽略评审，维持现状
- **选择**: B
- **拒绝 A 的原因**: 违反 YAGNI；多个建议属于过度抽象（凭证目录显式化、`--fix` flag、冷启动 UI），反而增加维护面
- **拒绝 C 的原因**: 4 条确为真 bug（脚本数错、约束清单分歧、文档悬空引用、I9 invariant 0 测试），静默发版会遗留
- **反悔代价**: 低——所有被拒的建议若将来真触发场景可单独补；被接受的修复都是小改动
- **派生原则（写入 feedback memory 备选）**: 评审反馈按"evaluator 视角匹配度"加权——同一条建议在银行系统 = P0，在个人 markdown 工具 = P3
